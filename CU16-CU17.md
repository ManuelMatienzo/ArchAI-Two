# CU-16 y CU-17: previsualización y moderación

## Uso

1. Iniciar sesión y abrir un diagrama guardado del proyecto en una sala colaborativa.
2. Pedir una propuesta a @ArchAI usando Local o Nube y pulsar **Ver en pizarra**.
3. El borrador aparece con las mismas tarjetas UML del estudio, borde discontinuo y distintivo **Propuesta IA**. Todos los participantes de la sala reciben el mismo estado. Mover sus clases no modifica el diagrama oficial.
4. En el panel izquierdo, **Revisión de propuesta** permite inspeccionar, editar y seleccionar clases/relaciones. **Conversación** conserva las preguntas y respuestas de la sesión.
5. **Aprobar selección** incorpora solo lo seleccionado y válido, guarda el diagrama y crea una versión. El resto permanece pendiente; una relación pendiente puede aprobarse después de sus clases.
6. **Rechazar pendientes** elimina únicamente el borrador pendiente. No revierte lo aprobado anteriormente.
7. **Con feedback** conserva la corrección y pide una nueva propuesta sobre los elementos pendientes usando el motor seleccionado. Si hay una consulta en curso se ofrece reintentar la corrección.

**Ocultar** controla solo la visibilidad personal. **Validar contra el modelo actual** permite revisar una propuesta después de cambios concurrentes; las colisiones deben resolverse en el editor. Si otra sesión guardó el mismo diagrama, primero se recupera ese guardado y se requiere una nueva revisión.

La edición reutiliza las tarjetas, conexiones, fuentes, superficies y botones existentes. La barra contextual respeta el dock inferior; el panel separa conversación y revisión para conservar espacio de edición en ventanas pequeñas.

## Autorización y persistencia

La API de revisión valida JWT y permisos del proyecto: propietario, administrador o editor pueden moderar; lector solo consulta. Un diagrama personal sin proyecto requiere ser su creador. El selector de rol de demostración del frontend no concede permisos de moderación en el servidor.

Los comandos HTTP se publican por STOMP una vez confirmados. La aprobación es transaccional, conserva los elementos oficiales no afectados y utiliza identificadores de operación para recuperar reintentos sin duplicar versiones. Se valida tanto la revisión del borrador como el diagrama oficial. Los guardados antiguos no pueden sobrescribir una aprobación más reciente.

Se reutilizan las tablas de diagramas y versiones: no hay migraciones nuevas. Los borradores, decisiones e identificadores de operación permanecen en memoria en la instancia del backend. Reconectar recupera ese estado mientras el servidor conserve la sala; reiniciarlo elimina los borradores. La persistencia contigua de propuestas corresponde a CU-21.

Para estas comprobaciones se utiliza el perfil **local-test con H2**, sin escribir en la base remota del `.env`. H2 en memoria también pierde los datos de prueba al detener el backend.

## Verificación técnica

Desde `backend`:

```powershell
mvn '-Dmaven.repo.local=../.maven-cache' '-Dspring.profiles.active=local-test' clean test
mvn '-Dmaven.repo.local=../.maven-cache' '-Dspring-boot.run.profiles=local-test' spring-boot:run
```

Surefire carga el agente Byte Buddy al arrancar para evitar el bloqueo de adjunto dinámico observado en Windows/JDK 21. Usa la versión de dependencias administrada por Spring Boot, sin una ruta específica del equipo.

Desde `frontend`, con Node compatible:

```powershell
node tests/proposalAgent.test.mjs
node tests/proposalDraft.test.mjs
node tests/proposalRendering.test.mjs
npm run build
```

`tests/proposalReview.integration.mjs` requiere el backend **local-test** en `127.0.0.1:8000`. Crea usuarios/proyecto sintéticos en H2, conecta tres clientes STOMP y comprueba aislamiento, permisos, aprobación parcial y versionado. No usar contra un servidor de producción. Su sesión auxiliar se guarda bajo `node_modules/.cache`, excluido de Git.

## Guion manual de aceptación

| Acción | Resultado esperado |
| --- | --- |
| Dos usuarios en la misma sala; otro en una distinta | Solo la primera sala recibe el borrador y la decisión. |
| Proponer Receta enlazada a Paciente existente | Se conserva Paciente y se muestra su relación con la clase propuesta. |
| Editar/mover el borrador | Se comparte el cambio provisional; el modelo oficial conserva sus clases y miembros. |
| Desmarcar una relación y aprobar su clase | La clase se vuelve oficial; la relación queda pendiente. |
| Aprobar la relación restante | Se conecta usando los identificadores oficiales de las clases ya aprobadas. |
| Rechazar los elementos pendientes | Desaparece el borrador; lo previamente aprobado permanece. |
| Dos aprobaciones simultáneas o doble clic | Una aplicación y una versión por operación. |
| Modificar el modelo mientras se revisa la propuesta | Se solicita revisar/validar antes de aprobar; no sobrescribe cambios silenciosamente. |
| Fallar el guardado | El borrador se conserva y no aparece una aprobación exitosa. |
| Reconectar | Se recuperan borrador, posiciones y revisión de la instancia activa. |
| Enviar feedback | Se consulta una vez al motor seleccionado y el resultado se comparte. |

Para conservar pruebas sin depender de Gemini se puede usar Ollama con `qwen3.5:4b`. Previsualizar, editar, aprobar y rechazar sin feedback no generan nuevas consultas. Incorporar cambios estructurales al diagrama oficial puede activar las recomendaciones automáticas existentes de CU-15.
